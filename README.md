# P24 — Protocol or Architecture?

CISC 473 Deep Learning, Fall 2026. Sneh Mangroliya, Tirthkumar Patel.

A controlled re-evaluation of PatchTST, iTransformer and DLinear (with Autoformer as the
older baseline) on ETTh1/ETTm1, and a new ten-zone Ontario demand dataset (ON-Zonal)
built from IESO's public reports.

## One command

```bash
pip install -r requirements.txt
./reproduce.sh tables   # rebuild every table, the ablation figure and the GPU-time summary from results/ (no GPU)
./reproduce.sh all      # setup + ON-Zonal + Weather + every plan + timing + tables + figures (GPU; days of compute)
```

`./reproduce.sh tables` runs `report_tables.py results` (writes `tables/*.tex`, the midterm
report's Tables 1–4 and 10, and prints every number quoted in the text), `plot_ablation.py
results` (`figures/fig_ablation.pdf`, Figure 1) and `budget.py results`.

`results/` holds every logged run: `runs_A.csv` (ETTh1 reproduction and F1, Job A),
`runs_B.csv` (ON-Zonal RQ2, Job B), `runs_C.csv` (PatchTST ablation, Job C), plus the
ON-Zonal build outputs (`onzonal_checks.json`, `onzonal_stats.json`,
`onzonal_seasonal_naive.csv`, `fig_onzonal_corr.png` = Figure 2). Console logs for Jobs B
and C are in `logs/`. All runs used NVIDIA Tesla T4 GPUs on Kaggle and Colab. Jobs A and C
share six PatchTST runs; `report_tables.py` checks that they agree exactly (they do).
New jobs add `results/runs_<JOB>.csv` and `logs/logs_<JOB>/` (see the notebook's JOB table).

## Re-run the experiments

```bash
python p24.py setup                                   # repos + ETT data, verified
python p24.py plans                                   # every plan, its plan ID, default seeds, run count
python p24.py run --plan V                            # validation gate: prints PASS/FAIL (run first)
python p24.py run --plan sameL                        # any plan; default seeds = the plan's own
python p24.py run --plan sameL --list                 # print the run_ids only
python p24.py run --plan sameL --smoke                # 1 epoch, logged to results/smoke_runs.csv only
python onzonal.py                                     # build ON-Zonal (needs internet) before any onzonal_* plan
python p24.py weather-data                            # Weather (see Data); the weather plans call it themselves
python p24.py f3select results                        # F3: lowest validation loss per (model, H), seed 2021
```

## The results CSV

One row per run. Columns 1–22 are unchanged. Columns added on branch `final-runs` (blank in
every row logged before it):

| Column | Meaning |
|---|---|
| `mse_official`, `mae_official`, `n_scored_official` | Only when `scoring = all+official`: the score of the official PatchTST test loader (first `n_scored_official` windows). |
| `scoring` | `official`: the model's own test loader, unchanged. `all`: every window, batch-size-1 re-score of a checkpoint (mode `rescore_bs1`). `all+official`: PatchTST dual scoring, one test pass. |
| `variant` | Empty for the unmodified model, else e.g. `nots`, `ci`, `cal-hour-dow-hol`, `cal-none`, `lr3e-05`. Also appended to `run_id` and to `--des` (own checkpoint folder). |
| `vali_loss_best` | Lowest validation loss over the epochs (the early-stopping checkpoint); used by F3. |

**What `mse` means, in old and new rows alike:** `mse` and `mae` are computed over
`n_scored` of the `n_test_windows` test windows; every window counts if and only if
`n_scored == n_test_windows`. Concretely:

| Row | `mse` is |
|---|---|
| old PatchTST `train` rows (`scoring` blank) | official loader: last partial batch dropped (`n_scored < n_test_windows`) |
| old `rescore_bs1` rows | every window (batch size 1) |
| DLinear, Autoformer, iTransformer (old and new) | official loader, which scores every window |
| new PatchTST training rows (`all+official`) | **every window**; the official-loader score is in `mse_official` |

`report_tables.py` derives two scores for every row (`mse_off`: official loader;
`mse_all`: every window), never mixes them in one table, and states which one each table
uses. Rows with the same `run_id` from different jobs (deliberate re-runs) must agree on both
scores, or the build stops.

**Why the official subset of a dual-scored run is exactly the official loader's result.**
PatchTST's test loader (`data_provider/data_factory.py:17-20`) is
`DataLoader(test_set, batch_size=b, shuffle=False, drop_last=True)`. With `shuffle=False` the
sampler is sequential, so the batches are windows `[0, b)`, `[b, 2b)`, …; `drop_last` only
decides whether the final short batch `[⌊n/b⌋·b, n)` is yielded at the end. The dual-scoring
loader is the same call with `drop_last=False`, so its first ⌊n/b⌋ batches hold the same
windows in the same order. `test()` runs the model in `eval()` mode under `no_grad()`: dropout
is off and BatchNorm uses its running statistics, and RevIN, patching and attention act on one
window at a time, so each prediction depends only on its own window; identical batches give
identical predictions, and the extra batch comes after them. The first ⌊n/b⌋·b predictions are
therefore the official ones, and `metric()` on them gives the official MSE/MAE. Checked on CPU
byte for byte (`tests/output/test_flags_off.txt`), and on T4 by plan V. Only the test pass at
the end uses the new loader: the per-epoch "Test Loss" pass in `train()` keeps the official
loader, so training and its log are unchanged (and no DataLoader iterator is added or removed,
so the global RNG stream is untouched).

## Changes to the official code

`patch_repos.py` makes only these changes, and asserts that each one applied. Switches 4–7
are off by default; with all of them off, the code computes exactly what the official code
plus changes 1–3 computes (`tests/output/test_flags_off.txt`: identical logs and `pred.npy`).

1. `np.Inf` → `np.inf`, `df.drop([...], 1)` → `df.drop(columns=[...])`,
   `s.apply(f, 1)` → `s.apply(f)`, so the 2021–2023 code runs on numpy ≥ 2 and pandas ≥ 2.
   Added on `final-runs`: `to_offset('t')` → `to_offset('min')` in `utils/timefeatures.py`,
   because pandas ≥ 3 removed the `'t'` alias and Autoformer's ETTm1 script passes `--freq t`
   (it crashed at data loading); on pandas 2 the calendar features are byte-identical
   (`tests/output/test_freq_alias.txt`). The models, training loops and metrics are unchanged.
2. LTSF-Linear, Autoformer and iTransformer hard-code their seed (2021, 2021, 2023). They now
   read it from the `SEED` environment variable, with the original value as the default.
3. `P24_NO_TIMESTAMPS=1`: iTransformer does not receive its four calendar tokens (hour of day,
   day of week, day of month, day of year), exactly as its own code already does for the PEMS
   and Solar datasets. Only the `onzonal_nots` and `onzonal_seeds` plans set it.
4. `P24_ALL_WINDOWS=1` (PatchTST, `exp/exp_main.py` `test()`): dual scoring, explained above.
   `p24.py` sets it for every PatchTST training run.
5. `P24_EXPORT=1` (PatchTST, LTSF-Linear): also save `true.npy` (their line is commented out).
   With `export=True` in a plan, `p24.py` copies `pred.npy`/`true.npy` as one compressed
   `$P24_RESULTS/preds/<run_id>/pred_true.npz` plus the `test_results/*.pdf` plots. Predictions
   are on the z-scored scale; MW needs the training-split mean/std (`onzonal.py` `zscore_train`).
6. `--cal_hour`, `--cal_dow`, `--cal_holiday` (PatchTST+Cal, Objective 5). Learned embeddings
   `nn.Embedding(24,d)`, `(7,d)`, `(2,d)`, added to each patch token next to PatchTST's
   position embedding (`layers/PatchTST_backbone.py:165`), shared across channels, indexed by
   the timestamp of the patch's first step (`j·stride`). They are created after every baseline
   parameter and zero-initialised through `_weight=torch.zeros(...)`, which skips
   `reset_parameters()`, so building them draws no random number and the baseline
   initialisation and RNG stream are unchanged. The integer hour and day of week are
   recovered from the timeF features: `hour = round((x + 0.5)·23)` from
   `HourOfDay = index.hour / 23.0 - 0.5` (`utils/timefeatures.py:38`) and
   `dow = round((x + 0.5)·6)` from `DayOfWeek = index.dayofweek / 6.0 - 0.5`
   (`utils/timefeatures.py:45`, Monday = 0). With `--cal_holiday`, `Dataset_Custom` appends a 0/1
   column, the date's membership in `holidays.Canada(subdiv="ON")` (statutory holidays and
   their observed days; the Civic Holiday is not included), to the calendar features.
   `batch_x_mark` is passed to the model only when a flag is on (`exp/exp_main.py`, all 8 calls).
   Without a flag the argparse namespace has no `cal_*` entry (`argparse.SUPPRESS`), so even
   the printed "Args in experiment" line is unchanged. Added parameters: 24+7+2 = 33 × d_model
   for all three (ETTh1 hour+dow, d_model 16: 496; ON-Zonal full, d_model 128: 4,224; see
   `tests/output/test_cal.txt`).
7. `P24_ITR_CI=1` (iTransformer, Control 2): channel-independent iTransformer. After the
   normalisation, `[B, L, N]` becomes `[B·N, L, 1]` and the calendar tokens are repeated per
   variate, so each sequence holds one variate token plus its own calendar tokens; outputs are
   reshaped back to `[B, S, N]`. No parameter is added.

## Test-loader behaviour at the pinned commits (checked in `data_provider/data_factory.py`)

| Repo | Test batch size | `drop_last` on test |
|---|---|---|
| PatchTST | `--batch_size` (128) | **True**: the last partial batch is never scored (dual scoring adds it back, see above) |
| LTSF-Linear | `--batch_size` | False (changed from True on 2023-03-15, commit `6fe4c28`) |
| Autoformer | `--batch_size` | False (changed from True on 2022-12-22, commit `d910070`) |
| iTransformer | forced to 1 | True, but with batch size 1 nothing is dropped |

Factor F1 re-scored each PatchTST checkpoint with batch size 1 (rows `rescore_bs1`); new
PatchTST runs log both scores in one pass instead.

## Timing (`timing.py`)

Builds each configuration exactly as the plans train it (same arguments, the official run
script's own argparse block, the official `Model` class), feeds random tensors of the test
loop's shapes, and times `--warmup` untimed plus `--reps` timed forward passes, each between
`torch.cuda.synchronize()` calls; reports the median and quartiles in ms, plus the parameter
count. Untrained weights are fine: a forward pass does the same operations on tensors of the
same shapes whatever the weights hold (Autoformer's top-k lag selection always keeps a fixed
number of lags). Data loading and host-to-device copies are excluded. Compare only rows with
the same `device`.
